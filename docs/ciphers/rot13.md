# ROT13

> 分類：固定鍵的單表替換密碼。CipherTool 不需要自訂密鑰；加密與解密是同一個動作。

## 名稱、背景與定位

ROT13 的名稱直接說明它的規則：把英文字母旋轉（rotate）十三格。它是凱薩密碼的一個特例，因為英文字母表有二十六個字母，而十三正好是一半。A 變成 N、B 變成 O，直到 M 變成 Z；再往下的 N 又會變回 A。這個特性讓 ROT13 在歷史上常被當成一種「避免不小心看到答案」的遮罩，例如早期網路討論區會拿它隱藏笑話結局、謎題提示、劇情爆雷或不想直接顯示的文字。它從來不是安全通訊方案，而是一種約定俗成、任何讀者都能迅速還原的文字轉換。

ROT13 的流行也反映了工具與目的的差別。若目的是讓旁觀者不會一眼讀到內容，它非常方便：不需要交換密鑰，也不必記得採用哪一套表。但若目的是讓未授權者無法讀取，它幾乎沒有作用；看到 ROT13 的人只要再套一次 ROT13 就能還原。現在許多網站不再以它作遮罩，改用可點擊的劇透標籤或存取控制，但它仍是程式設計與古典密碼入門的經典例子。

## 為什麼同一個操作能加密也能解密

沿用 `A=0` 到 `Z=25` 的編號，ROT13 的公式是：

```text
R(x) = (x + 13) mod 26
```

把它連續做兩次：

```text
R(R(x)) = (x + 13 + 13) mod 26 = (x + 26) mod 26 = x
```

所以 ROT13 是一個自反函數（involution）：函數套用兩次會回到原值。一般凱薩密碼的加密要加 `k`、解密要減 `k`；ROT13 因為 `-13 mod 26` 仍等於 13，兩個方向自然重合。這個等式不是程式偷懶，而是二十六與十三的數學關係。小寫字母也依同一索引規則處理，大小寫保持不變；非 ASCII 英文字母則不屬於這個二十六字母的循環。

可以把字母表切成兩半來看：

```text
ABCDEFGHIJKLM
NOPQRSTUVWXYZ
```

上下對照，同一欄的兩個字母互換。`C` 對 `P`、`M` 對 `Z`、`N` 對 `A`。因此不必一格格數十三步，手算時也能先寫出這兩列來查表。這種固定配對還表示，ROT13 不存在「猜錯金鑰」的情況：只要確認文字使用的是標準 ROT13，結果唯一。

## 手算例子與資料處理規則

把 `Hello, World!` 套用 ROT13：`H→U`、`e→r`、`l→y`、`l→y`、`o→b`；空白和逗號保持原狀；`World` 變成 `Jbeyq`。結果為：

```text
原文：Hello, World!
ROT13：Uryyb, Jbeyq!
還原：Hello, World!
```

最後一行只要對中間一行再做一次同樣操作即可。試著對 `Uryyb` 逐字替換，會得到 `Hello`；這是檢查手算最直接的方法。數字 `2026`、中文 `密碼`、標點 `!?` 在 CipherTool 中會原樣保留，因為實作只針對 `A-Z` 和 `a-z`。若原句同時含有英文與中文，例如 `Meet 我 at 8`，ROT13 的輸出只會改變 `Meet` 與 `at`，這不是 Unicode 加密，也不會隱藏中文內容。

常見錯誤包括把 `Z` 往後移十三格後仍留在字母表尾端，或把小寫直接轉成大寫。標準 ROT13 必須繞回，並應保留大小寫。另一個誤解是以為 ROT13 需要「先加密再選擇解密模式」：在數學上兩者相同，介面即使顯示加密與解密選項，套用結果也會一致。這也使得它不適合需要不同發送者和接收者角色的安全系統。

## 在 CipherTool 中使用

在 GUI 選擇 Classical Cipher 類別的 ROT13，輸入文字並執行即可。它沒有位移、關鍵字、替換表或矩陣等可調參數；這是設計使然，不是功能缺漏。若你希望自行選擇位移量，例如轉 5 格或 19 格，應改用 [凱薩密碼](./caesar.md)。同樣地，若你希望不同字母位置使用不同的關鍵字，應研究維吉尼亞或 Autokey，而不是嘗試把 ROT13 疊很多次。

在教學活動中，ROT13 很適合驗證「可逆」與「安全」不是同義詞。可先讓同學把一句英文轉成 ROT13，再把紙條交給另一人；即使沒有任何額外資訊，對方只要知道 ROT13 這個名稱就能讀出內容。這說明安全模型必須假設攻擊者看得懂演算法與密文格式。工具介面的輸出複製功能也只是在複製可見文字，並沒有另行加上一層保護。

## 破解、限制與正確使用情境

ROT13 不需要密碼分析就能破解，因為它沒有可選擇的秘密。攻擊者可以透過已知規則立即還原，或單純再執行一次相同轉換。即使不知道它叫 ROT13，字母頻率、英文常見詞形和只有一種固定替換關係也很容易讓人識別。把文字做兩次 ROT13 甚至會直接回到原文；把它和 Base64、Hex 等編碼連用，也只是增加一點閱讀步驟，沒有建立密碼學安全性。

它的合理用途是低風險的社群禮貌：避免他人無意間看見謎底、梗圖答案或簡短的劇透提示，且參與者都理解這不是保密措施。在需要權限控制、機密性、身分驗證或防竄改時，它完全不合格。密碼、個人資料、API token、復原碼、商業文件和聊天內容都不應以 ROT13 儲存或傳送。真正的需求應改用經過審查的現代加密和合適的金鑰管理。

從學習角度來看，ROT13 的價值恰好在它的弱：一個小小的模運算公式就能展示置換、逆函數、字母表映射、資料保留規則與威脅模型。理解它之後，再比較有密鑰的凱薩、更多可能映射的單表替換，以及會隨位置變化的多表替換，就能看見古典密碼如何一步步提高複雜度，也能理解為什麼現代安全仍需要遠比這些方法嚴格得多的設計與驗證。

## 延伸練習與辨識方式

ROT13 最好的練習不是背表，而是驗證它的對稱性。任選一段只含英文的文字，先手動做一次，再把結果重新對照兩半字母表；你應該得到原句的每一個字元、大小寫與標點都完全一致。接著把同一句交給凱薩密碼並填入 shift 13，輸出也應一致。這個交叉驗證說明兩個工具在這組固定參數下描述的是相同轉換，只是 ROT13 把可選密鑰固定成了十三。

從密文辨識 ROT13 時，可以尋找一些常見配對。例如英文 `the` 會變為 `gur`，`hello` 會變為 `uryyb`，而 `test` 會變為 `grfg`。這些只是辨識線索，不能當成唯一證據；真正的確認方法是整段套用一次後是否得到有意義的文本。請避免把「看起來像亂碼」直接稱為加密，因為編碼、鍵盤誤輸入、其他替換法也可能產生類似外觀。名稱、規則與威脅模型必須一起看。

ROT13 對非英文字元不做映射亦帶來一個教學提醒：字母表不是自然界唯一的文字系統。中文沒有一個可直接對半的二十六格循環，日文、阿拉伯文、重音字母也各有不同的排序與正規化問題。把 ASCII 英文的規則擴張到所有 Unicode 字元，往往會造成不可預期的結果。CipherTool 選擇保留這些字元，讓行為容易理解且可逆；若練習題需要另一種字母表，必須明確定義其順序、大小與繞回方式。

還有一個常見迷思是「固定規則不用密鑰所以更方便」。方便的代價正是任何人都能讀；資訊安全裡，省掉秘密並不會神奇地產生保護。ROT13 適合作為公開社群的視覺遮罩，不適合作為存取控制。把這條界線記住，便能在看到任何新工具時先問：它是在改變表示、避免一眼看見，還是確實在對抗擁有演算法與電腦資源的攻擊者？三者需要的技術完全不同。
